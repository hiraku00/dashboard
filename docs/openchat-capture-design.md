# オープンチャット読み取り 方式変更の設計（全展開 → 一括スクロール撮影 → 画素でつなぐ → 1回OCR）

> **実装での変更点**: 撮影と読み取りは、全ノートを開いてから1回でつなぐのではなく、**ノートごと**（コメント欄を開き、「前のコメントを見る」を押し切ったあと、そのコメント欄だけを見出しから末尾まで撮る）に行う。押す操作と撮る操作を分ける方針（撮影中はクリックしない）、画素だけでつなぐ方式、1回のOCR（タイル2回読み）は設計どおり。差分取得の判断（台帳との照合）を既存の一覧走査のまま使えるため。スクロール量の合計は、どちらの方式でも各コメントを1回通るのでほぼ同じ。

- 状態: 設計（未実装）。2026-09-24
- 対象: `collector/line_openchat/`（読み取り部分）、Worker の一覧API、`/chikirin` の画面
- 前提となる設計: [chikirin-openchat.md](chikirin-openchat.md)（台帳・差分取得・同期API・安全の仕組みは、そのまま使う）

## 1. なぜ変えるか

今の方式は「1画面ずつOCRし、読んだ文字で前の画面との重なりを判定する」。実機で次の問題が続いた。

| 問題 | 原因 |
|---|---|
| 上下に往復し続ける | 同じ場所でもOCRの結果が揺れる（名前の読み違い、時刻の行の読み落とし、冒頭の欠け）。文字で重なりを判定すると「重なっていない」と誤判定し、戻って撮り直す |
| 同じコメントの二重計上・取りこぼし | 位置合わせの誤判定 |
| クリックとスクロールが交互で遅い | ノートごとに「開く→戻る→読む」を繰り返す |

新方式では、**重なりを画素で判定する**（文字の揺れの影響を受けない）。さらに、**先に全部を展開してから、上から下へ1回で撮る**。

## 2. 実機で確認した前提（2026-09-24、推測ではなく測定値）

| 項目 | 測定結果 | 設計への反映 |
|---|---|---|
| スクロール前後の画素の一致 | 重なり部分の85%の行が画素単位で完全に一致。残り15%は固定表示（見出し・＋ボタン）。2番目の候補は30%で、差が明確 | 画素の一致率でずれ幅を決める（§5） |
| 1回のスクロール量 | 6行→200px、9行→304px、12行→402px、24行→806px（Retina 2倍、1行≒33.5px≒16.8pt）。ほぼ一定 | 歩幅を行数で指定できる。ただし一定であることには依存しない（毎回、画素で測る） |
| 一覧の末尾 | それ以上スクロールしても、画像が変わらない（ずれ幅0） | 終端の判定 |
| 固定表示 | 上部の見出し（約58pt）。右下の＋ボタン（右端から約80pt×下端から約130pt）。スクロール中は右端にスクロールバーが出る | つなぎ合わせでは除外し、除外しない帯（安全帯）だけを使う（§5.2） |
| 複数のコメント欄を同時に開けるか | 開ける（以前の実機操作で、2つのノートのコメント欄が同時に開いた状態を確認済み） | 全展開してから撮影できる |
| コメント欄を開いた直後の表示 | 最新のコメント付近へ飛ぶ | 展開後に上へ戻って「前のコメントを見る」を押す（§4） |
| ディスプレイ | 内蔵（Retina 2倍）と外付け（1倍）。ウィンドウは移動しうる。幅も変わる（428pt→401pt） | 倍率とウィンドウ幅を、実行ごとに測る。右端基準の座標は幅からの相対値にする |
| Shottrの画像での検証 | 1倍・幅400・高さ51,644pxの1枚から、13ノートすべてで表示件数とコメント数が一致した（OCRを境目をずらして2回かける方式） | OCRの方式（§6）はこれを採用 |
| Shottrの弱点 | つなぎ目で、行の途中から二重に写る・崩れた行が混ざる | 自前の画素つなぎで、行の途中で切らない（§5.4） |

## 3. 全体の流れ

```
0. 前提の確認（LINE起動・ロック解除・権限・ノートウィンドウ）      … 既存(lineui.check_environment)
1. 調整（キャリブレーション）: 倍率・ウィンドウ幅・固定表示の範囲を測る  … 新規 §5.2
2. 展開パス（上→下、クリックあり）                                … 新規 §4
     - 一覧を上から下へ進みながら、各ノートを「あるべき状態」にする
       * 読む必要があるノート: コメント欄を開く → 「前のコメントを見る」を押し切る → 本文の「もっと見る」を押す
       * 読む必要がないノート: コメント欄が開いていれば閉じる（撮影量を減らす）
     - 範囲の終わり（§7）まで来たら止める
3. 撮影パス（上→下、クリックなし）                                 … 新規 §5
     - 先頭へ戻り、一定の歩幅で下へ。撮るたびに画素でずれ幅を測り、仮想の縦長画像につなぐ
     - 展開パスで止めた位置まで撮る
4. OCR（仮想の縦長画像を、重なり付きのタイルで2回読む）            … 新規 §6
5. 区切り（ノート/コメント/作者/バッジ/時刻/本文）                 … 既存parseを縦長画像向けに移す §8
6. 検証（ノートごとに、表示の件数 = 読んだコメント数）             … §9
7. 台帳に反映 → Portalへ送る                                         … 既存(ledger, uploader) そのまま
```

クリックは展開パスだけ、読み取りは撮影パスの後に1回だけ。撮影中はクリックしないので、画面の配置が撮影中に変わらない。

## 4. 展開パス

### 4.1 進め方

- 先頭から下へ、1画面ずつ進む（歩幅は安全帯の6割。§5.2）。進むたびに撮影し、**その画面だけ**をOCRして、次の3種類だけを探す。
  1. ノートの数の行（コメント数とコメントアイコンの位置）
  2. 「前のコメントを見る」
  3. 本文の「もっと見る」
- 処理済みのノートは、台帳と同じ照合（`identity.note_score`）で覚える。同じノートを二度処理しない。
- クリックは必ず `safety.guard_click` を通す（押せるのは、コメントアイコン・「前のコメントを見る」・「もっと見る」の3種類だけ。変更なし）。

### 4.2 1つのノートの処理（読む必要がある場合）

```
a. 本文に「もっと見る」があれば押す → 画面が落ち着くのを待つ（§4.4）
b. コメント欄が閉じていれば、コメントアイコンを押す → 落ち着くのを待つ
   （開くと最新のコメント付近へ飛ぶ）
c. 上へ戻りながら「前のコメントを見る」を探し、あれば押す。無くなるまで繰り返す。
   ノートの見出し（作者〜時刻行）が見えたら、このノートは完了
d. このノートの見出しの位置から、下への走査を再開する
```

- コメントの中に「もっと見る」（長いコメントの省略）があれば押す。実機ではまだ見ていないが、出た場合に備える。対象は、コメント欄の範囲内の「もっと見る」の文字だけ。
- 上へ戻る量の上限: 1つのノートにつき、コメント数×200pt＋2画面。超えたら、そのノートを「再確認待ち」にして次へ（無限に探さない）。

### 4.3 読む必要がないノート

- コメント欄が開いていれば（前回の実行や手作業で開いたまま）、コメントアイコンを押して閉じる。撮影パスの距離が短くなる。
- 閉じる操作も、許可済みの `toggle_comments` の範囲内。

### 4.4 画面が落ち着くのを待つ

クリックの後は、0.4秒ごとに撮影し、**2回続けて画素が同じ**になったら次へ進む（最大5秒）。「前のコメントを見る」は通信で読み込むため、固定の待ち時間にしない。

### 4.5 展開パスでのOCR

1画面ずつ読むが、使うのは「ボタンの文字の位置」と「数の行」だけ。本文は読まない。ここでOCRが揺れても、押す場所が見つからないだけで、データは壊れない。見つからなかった場合は、撮影パスの後の検証（§9）で件数の不一致として検出する。

## 5. 撮影パスとつなぎ合わせ

### 5.1 仮想の縦長画像

- 1枚の巨大な画像は作らない。Retina 2倍・幅802px・高さ10万pxだと、約320MBになるため。
- 代わりに「どの撮影画像の、どの行を、縦長画像のどの行に置くか」の対応表（ピース）を持つ。
  ```
  Piece(frame_id, src_y0, src_y1, dst_y0)   # 撮影画像 frame_id の [src_y0, src_y1) を、縦長画像の dst_y0 から置く
  ```
- 撮影画像はPNGで一時フォルダに保存し、OCRの後に削除する。失敗時だけ `collector/data/line_openchat/debug/`（7日で削除）に残す。
- OCRのタイルは、必要なときにピースから組み立てる。

### 5.2 調整（キャリブレーション、実行の最初に1回）

1. 1枚撮る。画像の幅 ÷ ウィンドウ幅（pt）を**倍率**とする（2.0 または 1.0）。
2. 6行スクロールしてもう1枚撮り、§5.3の方法でずれ幅dを測る。
3. **固定表示の範囲**: 2枚で「同じ位置の画素が一致し、かつ、ずらした位置では一致しない」行・領域を求める。
   - 上部の見出しの下端 `top_fixed`
   - 右下の＋ボタンの上端 `fab_top` と左端 `fab_left`
4. **安全帯** = [`top_fixed` + 8pt, `fab_top` − 8pt)。縦長画像には、各撮影画像の安全帯の行だけを使う。
5. **1行あたりの移動量** = d ÷ 6。歩幅（行数）を決めるのに使う。
6. 測定に失敗した場合（ずれ幅0が続く＝一覧の末尾にいる等）は、先頭へスクロールしてからやり直す。3回失敗したら中止する（理由を表示）。

### 5.3 ずれ幅の測定（前の撮影画像 A → 次の撮影画像 B）

- **比べる範囲**: 横は、左端から「ウィンドウ幅 − 16pt」まで（スクロールバーを除く）。縦は、安全帯。
- **各行の指紋**: その行の画素を、そのまま比べる（`numpy` で行ごとに差の合計が0かどうか）。
- **候補**: 0 < d ≤ 安全帯の高さ − 最小重なり（200pt×倍率）の範囲で、`A[安全帯の行 + d] == B[安全帯の行]` となる行の割合（一致率）を計算する。
  - 背景だけの行（無地）は、どのずれ幅でも一致してしまうので、**一致率の計算から除く**。
- **採用条件**（すべて満たすこと）:
  - 最良の一致率 ≥ 0.80（実測は0.85〜0.88。時刻の文字の更新「5分前→6分前」や、画像の読み込みで少し下がることがあるため）
  - 無地でない一致行が 40行以上
  - 最良の候補と、2番目の候補（最良から±2px以内を除く）の一致率の差 ≥ 0.25（実測は0.5以上。繰り返し模様での取り違えを防ぐ）
- **採用できない場合**: その画像は捨てる。前の位置から、歩幅を半分にして撮り直す。3回続けて失敗したら、撮影パスを中止する（理由を表示。部分的な結果は使わない）。
- **終端**: d = 0（画像が変わらない）が2回続いたら、一覧の末尾とみなす。

### 5.4 つなぎ方（重複が起きない理由）

- 縦長画像の各行は、**必ず1つの撮影画像からだけ**取る。重なり部分は「位置を測るため」だけに使い、画像を重ねて描かない。
- 撮影画像 k から新しく使う行は、前の画像の安全帯の下端より下にある行だけ（`src_y ≥ 安全帯下端 − d`）。
- **行の途中では切らない**: 切れ目は、画像Bの中で、使い始めの行の近く（±40pt）にある無地の行（全体が背景色）にずらす。文字の行の途中で画像が切り替わらないので、Shottrのような「行の途中からの二重写り」「崩れた行」が起きない。
- 安全帯だけを使うので、＋ボタン・見出し・スクロールバーは縦長画像に入らない。
- スクロールバーは、止めてから約0.8秒で消える。撮影はスクロール後0.8秒待ってから行う（スクロールバーの消え方は、実装時に実測して調整する）。

### 5.5 撮影パスの範囲

- 先頭（検索欄が見える位置）から、展開パスで止めた位置（§7）まで。
- 止める位置は、展開パスの最後に処理したノートの「次のノートの見出し」。撮影パスでは、その見出しがOCRで見えた時点で終える。
- 撮影の上限は1,500枚（安全弁）。

## 6. OCR（仮想の縦長画像）

Shottrの画像で検証した方式を、そのまま使う。

- タイルの高さは1,000pt相当、重なりは200pt。各タイルで、中央寄りの行だけを採用する（端で切れた行を避ける）。
- **境目をずらして2回読む**（オフセット0と400pt）。同じ位置（y差5pt以内、x差20pt以内）の行は、信頼度が高い方（同じなら長い方）を採用する。
  - 1回だけだと、境目の近くで行を読み落とすことを実画像で確認した（ちきりんのコメントの時刻の行が抜けた）。2回で解消した。
- **倍率**: 1倍の画像は3倍に拡大して読む。2倍の画像はそのまま読む（拡大すると時間がかかるだけで、精度は上がらない見込み。実装時に1回比較する）。
- 座標は、縦長画像のpt（倍率で割った値）で持つ。

## 7. 差分取得との関係（どこまで展開・撮影するか）

- **読む必要があるノート**（既存の `Ledger.needs_open` と同じ）:
  - 新しいノート
  - 表示の件数が台帳と違う
  - 表示の件数が読めない
  - 前回、件数が合わなかった（再確認待ち）
  - ちきりんのノートで、本文を全文取れていない
  - **ちきりんのコメントがあるノートで、スレッド主の本文を全文取れていない**（§10で追加）
- **範囲**:
  - 初回（`--first-run`）: 一覧の最後まで。
  - 2回目以降: 変化の無いノートが5件続き、かつ21日より古いノートに達したら、そこまで（既存の打ち切り条件と同じ）。
- 読む必要が無いノートは、展開パスで閉じる（§4.3）。撮影パスでは、見出しと数の行だけが写る（台帳の日時の正確化に使う）。

## 8. 区切りと抽出

既存の `parse.py` の規則を、縦長画像の座標に移す（1画面ずつではなく、全体を1回で区切る）。

- **時刻の行**が1つの投稿の終わり。時刻の行のx < 32pt ならノート、x ≈ 49pt ならコメント。
- **作者**: アバター（x=16〜40pt）が縦に22〜34pt続く位置の、名前の行。
- **ちきりん**: 青いバッジ（既存の判定のまま。実機では単色とグラデーションの2種類）。
- **ノート本文**: x < 32pt の行。「もっと見る」を押した後なので、全文が写っている。
- **リンクカード**: x ≥ 100pt の行は題名として、画像内の文字は捨てる（既存のまま）。
- **数の行**: 画素で、アイコンと数字の塊に分ける（既存。右端の塊は共有アイコン、1桁の数字は3回並べて読み、桁数が合わなければ不明）。
- **右端基準の座標**（いいね数、︙メニュー、折り返しの判定、＋ボタン）: ウィンドウ幅からの相対値にする（実機で幅が428pt→401ptに変わったため）。
- 画面の上端・下端で切れた投稿は、無くなる（縦長画像は一続きなので、途中で切れる投稿が無い。切れるのは撮影範囲の最後の1件だけで、それは次のノートの見出しより前で終えるので対象外）。

## 9. 検証（読み取りが正しいかの確認）

- **件数**: 読んだノートごとに、表示のコメント数と、区切ったコメントの数を比べる。
  - 一致すれば確定する（台帳に反映し、見えなくなったコメントは削除扱いにする。既存のまま）。
  - 一致しなければ、そのノートを再確認待ちにする。データは保存するが、削除扱いはしない（既存のまま）。
- **重複の検査**（念のため）: 1つの投稿の中に、同じ文（12文字以上）が2回現れたら警告する。画素でつないでいれば起きないはずなので、起きたら、つなぎ合わせの不具合として、デバッグ用の画像を残す。
- **本文の品質の目安**: OCRの信頼度が低い行の割合を、警告に出す（既存の `ocr_min_confidence`）。

## 10. スレッド主の番組情報（新しい要件）

ちきりんのコメントだけでは、何の番組か分からないことがある。そのため、**ちきりんが関わるノートは、スレッド主の投稿（番組の情報）も全文取得して、画面に表示する**。

- **取得**: 読むノートは、展開パスで必ず本文の「もっと見る」を押す（§4.2 a）。ちきりんが関わるかは、開いてから分かるため、読むノートはすべて全文を取る（手間はノートにつき1クリック）。
- **保存**: `openchat_notes.body_text`（既存の列）に全文、`body_complete=1`。スキーマの変更は無い。
- **API**: `GET /api/openchat/programs` が、**ちきりんが関わるノートについて**、スレッド主の本文（`noteBody`）を返す。
  - 一覧に載るのは、今と同じく「ちきりんのスレッド、または、ちきりんのコメントがあるノート」だけ。
  - ほかの人のコメントは、今と同じく返さない。
  - 変更点は「一覧に載るノートのスレッド主の本文を返す」ことだけ。検索の対象にも加える（番組名で探せるように）。
- **画面**: 番組カードの上部に「スレッド主の投稿（番組の情報）」を表示する（長い場合は折りたたむ）。その下に、ちきりんのコメントを並べる。ちきりん自身のスレッドは、今と同じ表示。
- **テストの変更**: 「ほかの人のノート本文は返さない」テストを、「一覧に載るノートの本文は返す／載らないノートの本文は、一覧にも検索にも出ない」に改める。

## 11. 失敗時の扱い

| 場面 | 動作 |
|---|---|
| 調整に失敗（倍率・固定表示が測れない） | 中止。理由を表示（例: 「ノートのウィンドウが小さすぎます」「スクロールしても画面が動きません」） |
| 展開パス: 押すべきボタンが見つからない | そのノートを再確認待ちにして、次へ進む |
| 展開パス: 画面が5秒たっても落ち着かない | そのまま進む（撮影パスの件数検証で検出する） |
| 撮影パス: ずれ幅を3回続けて測れない | 撮影パスを中止する。部分的な縦長画像は使わない（取りこぼしを保存しない）。デバッグ用の画像を残す |
| 件数の不一致 | そのノートを再確認待ち（削除扱いにしない） |
| ユーザーのマウス・キーボード操作 | その場で中断（既存）。台帳は、確定したノートまで保存済み |
| OCRの結果に重複の疑い | 警告とデバッグ用画像。そのノートは再確認待ち |

## 12. 所要時間の見積もり

実測値をもとにした見積もり（実装後に実測して更新する）。

| 段階 | 初回（16ノート・約200コメント） | 2回目以降（数ノートの変化） |
|---|---|---|
| 展開パス | クリック約40回 × 約1.5秒 ＋ 走査 ≒ 2〜3分 | 変化したノートだけ ≒ 30秒〜1分 |
| 撮影パス | 縦長画像 約5万pt（2倍で約10万px）、歩幅約560pt で約90枚 × 約1秒 ≒ 1.5分 | 閉じたノートは短い ≒ 30秒 |
| OCR | 2回読み ≒ 2〜3分（1倍・幅400・高さ5万pxで、実測1分55秒） | ≒ 30秒 |
| 合計 | 約6〜8分 | 約2分 |

## 13. 安全（LINEは参照のみ）

変更なし。押せるのは、コメントアイコン（開く・閉じる）・「前のコメントを見る」・「もっと見る」だけ。キーボードイベントは送らない。`tests/test_safety.py` のソース走査も、そのまま有効。

閉じる操作（§4.3）が加わるが、開く操作と同じコメントアイコンなので、許可の範囲は変わらない。

## 15. テスト計画

### 自動テスト（実機なし）

- **つなぎ合わせ**: 合成した縦長画像（PILで作る。架空の文字・アバター・バッジ・＋ボタン・見出し・スクロールバーを描く）を、ずらしながら切り出して、次を確かめる。
  - ずれ幅が一定の場合、ばらつく場合、末尾に達した場合
  - 途中で1行だけ変化する場合（時刻の更新）
  - 無地が続く場合
  - 繰り返し模様（同じ短文のコメントが続く）の場合
  - いずれも、元の画像と、行単位で完全に一致すること
- **重複なし**: つないだ画像をOCRした結果に、同じ文が二重に出ないこと。
- **展開パス**: シミュレーターで、閉じている・開いている・「前のコメントを見る」が複数回・本文の「もっと見る」・読む必要がないのに開いている、の各状態から、あるべき状態になること。押した場所が、すべて許可された場所であること。
- **実画像の回帰テスト**: Shottrの画像（`SCR-20260924-prma.png`）でOCR→区切りを行い、13ノートすべてで件数が一致することを確かめる。
  - 実在の参加者の投稿が写っているので、画像と期待値は Git管理外（`collector/data/line_openchat/fixtures/`）に置く。無い環境では、このテストは自動でスキップする。
- **既存のテスト**（台帳・照合・時刻・安全・送信・Worker・画面）は、そのまま通すこと。API・画面の変更分（§10）は、テストを改める。

### 実機での確認（あなたがMacを使わない時間に、私が行う）

1. 調整だけを実行し、倍率・固定表示の範囲・1行の移動量が、§2の測定値と合うこと。
2. 撮影パスだけを実行し（クリックなし）、一覧を閉じた状態で縦長画像を作る。見た目で、つなぎ目の二重写りが無いこと。
3. 展開パスを、`--max-notes 3` で実行し、あるべき状態になること。
4. 通しで `--dry-run --first-run` を実行し、全ノートで件数が一致すること。所要時間を記録する。
5. 2回目の実行で、何も開かず、短時間で終わること。

## 16. 未確認の点とリスク

| 点 | 対応 |
|---|---|
| スクロールバーが消えるまでの時間 | 実装時に実測。消えない場合は、安全帯の横幅から除く（今の設計でも、比較からは除外済み） |
| コメントの中の「もっと見る」があるか | 出た場合に備えて押す（§4.2）。無ければ何もしない |
| 非常に長いコメント（1画面を超える） | 縦長画像は一続きなので、そのまま読める（今の方式の弱点が無くなる） |
| 撮影中に新しいコメントが増える | 画素の一致率が下がる場所が出る。ずれ幅の測定に失敗した場合は、撮り直しで対応。件数の検証で検出する |
| 1倍ディスプレイでの精度 | Shottrの1倍の画像で検証済み。2倍のほうが確実なので、ウィンドウがどちらにあるかを出力に表示する |
| 一覧が非常に長くなったとき（数百ノート） | 2回目以降は範囲を絞る（§7）。初回だけ時間がかかる |

## 17. 実装の順序

1. `capture.py`: 調整・ずれ幅の測定・つなぎ合わせ（合成画像のテストが先）
2. `tallocr.py`: Shottrの画像での回帰テストが通ること
3. `parse.py` を縦長画像の座標に対応させ、右端基準の座標をウィンドウ幅からの相対値にする
4. 実機で、調整と撮影パスだけを確認する（§15 実機 1・2）
5. `expand.py`: 展開パス（シミュレーターのテストが先）
6. `session.py` を差し替え（展開 → 撮影 → OCR → 区切り → 検証 → 台帳）
7. 実機での通し確認（§15 実機 3〜5）
8. §10 のAPI・画面の変更と、テストの修正
9. 画面からの実行の部品を、このブランチから外す
10. ドキュメントの更新、コミット・PRの前に内容をご報告
