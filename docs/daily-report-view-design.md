# 作業日報（auto-daily-report）の表示設計

[取り込み設計](daily-report-ingest-design.md)でD1に入れた日報を、**1日の詳細**と**週・月のサマリ（ダッシュボード）**として表示する。本書は画面・グラフ形式・読み取りクエリ・集計の設計で、実装はまだ（§10の順で進める）。

## 1. 前提にした実データの形（2026-10-22、手元の204件を解析して確認）

| 項目 | 値 | 設計への影響 |
| --- | --- | --- |
| 期間 | 2025-12-23〜2026-10-21、204件 | 2026-06は0件、3〜5月・8月は月に12〜14日欠ける。**「日報なし」の日を普通に出す**必要がある |
| 記録時間 | 中央値13h10m（p10 6h22m、最大23h36m） | 時間軸は日をまたがない（0時越えは0件）。表示範囲は期間内の最早開始〜最遅終了を時間単位に丸める（たいてい7〜24時） |
| 欠落（ログなし） | 中央値2h33m、p90 7h09m | 欠落は小さくない。**活動時間と欠落を分けて見せ、欠落を「サボり」に見せない** |
| 活動時間（タグの合計） | 平均9h11m/日、**標準偏差3h07m** | 日ごとのばらつきが大きい。5日分の平均でも標準誤差は約1h24m で、**週と週の差の大半は誤差の範囲**（§3.2） |
| 1日に付くタグ | 平均6.1個、うち5%未満が1.2個 | 1日の内訳を円で描くと、細い扇が毎日1〜2枚できる |
| 時間帯の行 | 1日平均9.3行 | 1日のタイムラインは粗い帯で十分。週7日を縦に並べても見やすい |
| 作業項目 | 1日平均7.6項目・4.7見出し | 「何をしたか」は見出し（`category`）単位で読ませる |

| タグ別の時間（全期間） | 視聴36%、英語18%、連絡8.8%、AI 7.0%、`other` 1.5% | 視聴が大きく、グループ単位でも偏る。タグ単位の内訳を必ず併記する |

## 2. 方向宣言

- ジョブ: 1日を開けば「何に何時間使い、何をして、何を学んだか」が読め、週・月を開けば「時間の配分」「いつやっているか」「最近の流れ」がひと目で分かる。
- レジスター: 主=精密、副=親愛。自分の記録を振り返る道具で、欠落や視聴の多さを責めない。増減に良し悪しの色（緑・赤）を付けない。
- サーフェス: web（ダッシュボード＋読み物）。既存のポータル（`app/globals.css` の `--bg` `--surface` `--ink` `--blue` など）に乗せる。
- パレット（グループの色、Coveの固定順。`dataviz` の validator で light の CVD・識別は合格、3色が地とのコントラスト3:1未満のため**凡例に数値・直接ラベルを必ず付ける**）:

  | グループ | 色 | タグ |
  | --- | --- | --- |
  | 学習 `study` | 青 `#2a78d6` | 英語、ROS 2、電子工作、CS |
  | 開発 `dev` | 橙 `#eb6834` | dashboard、TextTube、manage-asset、スクレイピング、ジムアプリ、日報ツール、Mulmo、AI、PC、開発（その他） |
  | お金 `money` | 緑青 `#1baf7a` | 資産・お金 |
  | 生活 `life` | 黄 `#eda100` | 旅行・住まい、買い物、メモ・習慣、連絡・SNS |
  | 視聴 `media` | 桃 `#e87ba4` | 動画・番組視聴 |
  | その他 `other` | 灰 `--faint` | どれにも当たらない |
  | 欠落 | 斜線（灰の45°ハッチ） | `（ログなし）` の時間帯。色ではなく模様で区別する |
  | 比較の基準 | 濃い灰の縦線（目盛り） | 前の期間、または直近28日の1日平均。**どの画面でもこの記号だけが「比べる相手」を表す** |

  タグはグループの色の濃淡で塗り分けない（20色は見分けられない）。タグは**行ラベル＋グループ色**で識別する。dark modeでは同じ順の dark 値（`#3987e5` `#d95926` `#199e70` `#c98500` `#d55181`）を使う。
- タイポ: 既存の日本語サンセリフ。時間・件数は `tabular-nums`。**主数値は画面に1つだけ大きく**、残りは一段小さい行で上から読む。
- 余白リズム: 8pxグリッド。カード間16px。スマホは左右16px、横スクロールなし。
- モーション: 160ms ease-out。ホバー・期間切り替えの状態変化だけ。
- シグネチャー: **週のタイムライン**（7日×時間軸の帯。色＝グループ、斜線＝欠落、破線の空行＝日報なし）。日の詳細でも同じ帯を1本で使い、週と日が同じ見た目でつながる。
- 禁じ手: 円グラフ・ドーナツ・ツリーマップを内訳に使うこと（§3）、欠落を赤で塗ること、増減を緑・赤で塗ること、期間の日数が違うのに合計どうしで比べること、2軸のグラフ、日報の本文をURLのクエリに入れること。

## 3. グラフ形式の検討

### 3.1 問いごとの比較

先に「その図で何を読み取るか（問い）」を決め、問いごとに候補を比べた。判断の物差しは、(a) 読み取りの正確さ（位置・長さ＞角度・面積・色の濃さ。Cleveland & McGill 1984 の知覚の順位）、(b) 期間どうしで並べて比べられるか、(c) 小さい項目・欠けた日で破綻しないか、(d) スマホ幅（343px）で読めるか。

| 問い | 候補 | 採用 | 理由 |
| --- | --- | --- | --- |
| **Q1 何にどれだけ使ったか（グループの配分）** | 円／ドーナツ、ツリーマップ、ワッフル（1マス＝1%）、100%積み上げ横棒 | **100%積み上げ横棒を今期・前期の2本、同じ幅で上下に揃える** | 配分の図で一番知りたいのは「前と比べて変わったか」。円は角度で読むので正確さが劣り、2枚並べても扇の位置がずれて比べられない。横棒なら左端が揃うので、先頭の学習の伸び縮みは長さで、2番目以降も境目の位置で比べられる。ワッフルは1枚なら分かりやすいが、2枚の比較は数えることになる。ツリーマップは面積で読むうえ、お金（3%）のような小さい項目にラベルが入らない |
| **Q2 タグごとの量と、前との差** | 横棒＋差の数字、ドットプロット（ダンベル）、スロープグラフ、**横棒＋前期の目盛り（ブレットグラフ）** | **ブレットグラフ風: 今期の横棒に、前期の1日平均を縦線の目盛りで重ねる。グループの見出しの下にタグをまとめる** | 量（長さ）と差（棒の先と目盛りのずれ）を**同じ軸の位置**で読める。差を数字だけで出す案は、数字を1つずつ読んで比べることになる。ダンベルは差は読みやすいが量の印象が弱く、スロープは2点しかないと線が交差して読みにくい。20タグを1列の順位に並べるより、グループの見出しにまとめた方が構造が見える（§4 近接） |
| **Q3 いつやっているか（週）** | ガント型の帯（日×時刻）、24時間の円形時計、ヒートマップ（日×1時間） | **ガント型の帯（7行）** | 円形時計は見た目は良いが、日を並べて比べられず、角度で読む。ヒートマップは1時間ごとに丸めるので、「9:00〜10:30」が崩れる。帯なら時刻（位置）・長さ・内容（色）が全部そのまま読め、行のクリックで日の詳細へ移れる |
| **Q3' いつやっているか（月）** | 30行の帯、**時刻別の平均構成（1時間ごとの積み上げ縦棒）** | **時刻別プロファイル**（横軸7〜24時、縦軸＝その1時間の平均分/日、0〜60分） | 30行の帯は生データで、「朝は英語、夜は視聴」のような**傾向**は目で平均しないと分からない。1時間ごとに平均した積み上げ縦棒なら傾向が直接見える。横軸は週の帯と同じ時刻なので、見方を覚え直さずに済む |
| **Q4 日ごとの量（月）** | カレンダーのヒートマップ、**日ごとの積み上げ縦棒** | **積み上げ縦棒（30本）**。土日の列に薄い地、日報なしは破線の空き枠 | カレンダーは量を色の濃さで表すので正確さが一番低い（5段階に丸める）。縦棒なら量は長さ、内訳は色で同時に読め、欠けた日も空き枠として見える。曜日の並び（カレンダーの利点）は土日の地で補う。各棒はクリックで日の詳細へ |
| **Q5 最近の流れ（12週・12か月）** | 積み上げ面、5本の折れ線、**スモールマルチプル（グループごとの小さな折れ線×5、縦軸共通）** | **スモールマルチプル** | 積み上げ面は下のグループ以外の基線が波打ち、増減を読み違える。5本の折れ線は交差して絡む。グループごとに分け、縦軸をそろえれば、各グループの増減と、グループ間の量の差の両方が読める |
| **Q6 アプリ（週）** | 使った日数の横棒、**日×アプリの点の行列** | **週は点の行列**（行＝アプリ上位8、列＝月〜日、使った日を塗る）、**月は使った日数の横棒** | 週の「使った日数」は0〜7の整数なので、横棒は点の数と変わらない。点にすれば同じ幅で「どの日に使ったか」まで分かる。月は30列で細かすぎるので横棒にする |
| **Q7 主数値** | 同じ大きさのタイル4枚、**主数値1つ＋小さな補助3つ** | **「1日平均の活動時間」を主数値にし、直近8期間のスパークラインを添える** | 4枚が同じ重みだと、どれから読むか分からない（§4 対比）。合計は日報の日数に左右されるので、期間どうしで比べられる1日平均を主にする |

### 3.2 円グラフを使わない理由（まとめ）

円グラフが向くのは「1枚だけ」「2〜3項目」「およそ半分・3分の1といった割合を伝えたい」ときに限られる。この画面はどれにも当たらない。

1. **比べるのが主な目的**: 配分は前の期間と比べて初めて意味がある。円を2枚並べても、2枚目以降の扇は始まりの角度がずれ、角度の差は読み取れない。
2. **項目が多く、小さい**: 1日に付くタグは平均6.1個で、うち1.2個は5%未満。グループ（5＋その他）でも、お金は3%前後の細い扇になり、ラベルが入らない。
3. **正確さ**: 角度・面積は長さ・位置より読み取りの誤差が大きい。100%横棒なら、同じ面積で長さとして読める。
4. **内訳はほかの図でも見せている**: 日の詳細では、タイムラインの帯がすでに1日の内訳を長さで表している。円を足すと同じ情報が2回出て、しかも精度の低い方になる。

ドーナツの中央に合計を置く案も、主数値（Q7）と重なるだけなので採らない。

### 3.3 統計上の扱い

- **比べる単位は1日平均**: 日報が無い日が多く（月に最大14日欠ける）、今週は途中のこともあるので、合計どうしは比べない。主数値・ブレットの目盛り・スモールマルチプルは、どれも「日報のある日の1日平均」で揃える。合計は補助の数字として添える。
- **差を強調しない**: 1日の活動時間の標準偏差は3h07mあり、5日分の平均でも標準誤差は約1h24mある。週と週の「+42分」は、ほとんどが日ごとのばらつきの範囲に収まる。そのため差は色で塗らず、目盛りとのずれ（位置）で控えめに見せる。流れはQ5の12期間で読む。
- **少ない日数では比較を薄くする**: 前の期間の日報が3日未満なら、目盛りを点線にし「参考」と添える。0日なら目盛りを出さない。
- **欠落は配分の分母に入れない**: 欠落はログの取りこぼしで、行動ではない。100%横棒・ブレットはタグの時間（活動時間）だけを分母にし、欠落は主数値の補助（「ログなし 9h12m・記録の22%」）に出す。
- **複数タグの等分**: 1つの時間帯に複数のタグが付くと、時間をタグ数で等分している（`tagDailyReport()`）。ツールチップに「複数のタグは等分」と添え、数字が実際の配分の推定であることを隠さない。
- **時刻別プロファイルの計算**: 各時間帯を1時間の区切りに重なった分だけ配り、日報のある日数で割る。欠落の時間は数えない（その時間帯の棒が低いのは、記録が無いかログなしだったため。ツールチップで「この時間に記録があった日 n日」を出す）。

## 4. レイアウトの原則（ノンデザイナーズ・デザインブックの4原則）

| 原則 | この画面での具体 |
| --- | --- |
| **近接**（関係するものを近づけ、無関係なものを離す） | 主数値とその比較（前期・スパークライン）を1つのかたまりにする。凡例は離れた場所に置かず、棒の横に値と一緒に書く（直接ラベル）。タグはグループの見出しの下にまとめる。ブロック間は24px、ブロック内の行間は8pxとし、余白の差でかたまりを見せる（罫線で囲みすぎない） |
| **整列**（すべての要素を何かの線に揃える） | ラベルの左端、棒の始まり（x=0）、数字の右端の3本の線をページ全体で共有する。週の帯・時刻別プロファイル・日の帯は**同じ時刻の横軸**で、上下に置いたとき目盛りが揃う。中央揃えは使わない（期間の表示も左揃え） |
| **反復**（同じ意味には同じ見た目を繰り返す） | グループの色、欠落の斜線、比較の目盛り、時間の表記（`10h33m`）、タグのチップ、行の高さ（28px）を全画面で同じにする。週の帯の1行と日の詳細の帯は同じ部品。 |
| **対比**（違うものははっきり違えて見せる） | 主数値は1つだけ大きく（他の数字の2倍以上）。今期の棒は彩度の高いグループ色、前期は濃い灰の細い目盛り。選択中の日・タグ以外は彩度を落とす（`?tag=` のとき）。弱い差（14pxと15px、灰と少し濃い灰）は作らない |

### 6.2 月

週と同じ順で、次の2つだけ差し替える。
- 「いつやったか」→ **時刻別プロファイル**（Q3'）。横軸は週の帯と同じ。
- 週の帯の位置に → **日ごとの積み上げ縦棒**（Q4）。棒のクリックで日の詳細へ。
- アプリは点の行列ではなく「使った日数」の横棒。「最近の流れ」は12か月。

### 6.3 各ブロックの決め事

**主数値**
- 1日平均の活動時間 = 期間の `SUM(tag_days.minutes)` ÷ 日報のある日数。内訳と必ず一致させるため、`recorded_minutes − gap_minutes` ではなくタグの合計を使う。
- 下に「前週 9h51m」をそのまま書く（増減の矢印・色は付けない、§3.3）。スパークラインは直近8期間の1日平均で、今期の点だけ色を付ける。
- 補助（右の列、一段小さい）: 合計、ログなし（記録の何%）、日報の日数（欠けた曜日、またはまだ来ていない日）。

**時間の配分（Q1＋Q2）**
- 100%横棒2本（今期・前期）。各区間に「学習 30%」を直接ラベル（入らない幅なら棒の右に並べる）。前期の日報が0日なら1本だけ。
- その下にブレットグラフ。グループの見出し行（グループ色の太い棒）→ 配下のタグ（同じ色の細い棒）。グループは今期の時間順、タグはグループ内で時間順。今期0分のタグは出さない。`other` は最後に「その他」。
- 棒の長さは**1日平均**。右に「1日平均」「合計」の2列の数字。目盛りは前期の1日平均。

**週の帯（Q3）**
- 7行（月〜日）。横軸は期間内の最早開始〜最遅終了を時間単位に丸めた範囲。時間帯1行を帯1つで描き、タグが複数なら帯をタグ数で等分して塗る（数字の数え方と見た目を一致させる）。タグ無しは灰、`is_gap` は斜線。
- 帯のホバーで「15:00〜17:00 2h ／ dashboardの改善… ／ dashboard・AI（複数のタグは等分）」。行のクリックで日の詳細へ。
- 日報なしの日は破線の空行に「日報なし」。まだ来ていない日は行ごと薄くし、帯を描かない。行の右端にその日の活動時間。

**時刻別プロファイル（Q3'、月）**: §3.3 の計算。1時間ごとの積み上げ縦棒、縦軸は0〜60分固定（月をまたいで同じ目盛りで比べられる）。

**日ごとの積み上げ縦棒（Q4、月）**: 縦軸は活動時間（時間）、グループで積み上げ、区間の間に2pxの隙間。土日の列に薄い地。日報なしは破線の空き枠。

**やったこと**
- `work_items` を `category`（見出し）でまとめ、見出しごとに出てきた日のチップと、最初の箇条書き1件。見出しの表記はLLMが毎日変えるので**名寄せはしない**。主タグのグループ色の点を付け、配分と同じグループ順→日付順に並べ、同じ話題が近くに来るようにする。
- 週は全件、月は上位20件＋「もっと見る」（クライアントで開く）。

**アプリ（Q6）**: `app_key` ごと、上位8。表示名はその期間で最も多い `app_name`（`／` の前）。週は点の行列＋右に日数、月は日数の横棒。使用回数は出さない（揺れが大きい。日の詳細の表で原文を見られる）。

**最近の流れ（Q5）**: グループごとの小さな折れ線5枚を横に並べる（スマホは2〜3列で折り返す）。縦軸は5枚共通（1日平均の時間）。今期の点に色、それ以外は線だけ。

**知見・メモ**: 新しい日付順。日付をリンクにして日の詳細へ。週は全件、月は10件＋「もっと見る」。

### 6.4 空・異常のとき

| 状態 | 表示 |
| --- | --- |
| 期間に日報が0件 | 主数値は「—」、本文の代わりに「この期間の日報はありません」＋直近の日報がある期間へのリンク |
| `parse_status='partial'` の日 | 帯の行・縦棒に小さな注意マーク。日の詳細で警告を表示 |
| `parse_status='failed'` の日 | 集計から自然に外れる（正規化行が無い）。行に「解析できず」、日の詳細は本文だけ出す |

- 帯はダッシュボードの週の帯と同じ部品（1行版）。帯のホバー／タップで表の該当行を強調し、表の行のホバーで帯を強調する（クライアント島はここだけ）。
- 「この日の配分」はダッシュボードと同じブレット。目盛りは**直近28日の1日平均**（その日が普段と比べてどうかを見る）。日の詳細には期間が無いので、比べる相手を「直近28日」に決め、凡例に明記する。
- 表の行は時間帯・所要・作業内容・タグのチップ。欠落行は斜線の背景で、文言は原文のまま。
- 「原本を表示」は既定で閉じる。描画は TextTube の `app/text-tube/markdown-renderer.tsx`（GFM表を描ける）を使う。節5（作業中だったファイル）は正規化していないので、ここでだけ読める。

- `partial` なら警告（`parse_warnings`）を折りたたみで表示。`failed` なら上部に注意を出し、原本を開いた状態で表示。

## 9. 読み取りクエリと集計

### 9.1 クエリ（`app/lib/queries/daily-report.ts`）

既存ページと同じく Server Component から直接D1を読む（`app/todo/page.tsx` と同じ形。失敗時は `null` を返して空表示）。1画面＝**1回の `env.DB.batch`**。ブラウザ用のGET APIは作らない（取り込みAPIは service token 専用で、表示に別経路が要らない）。

```sql
-- 1 日ごとの見出し情報(本文 markdown は読まない)。今期と前期をまとめて1本
SELECT report_date, record_start, record_end, recorded_minutes, gap_minutes, parse_status
  FROM daily_reports WHERE report_date BETWEEN ? AND ?;
-- 2 タグ×日(今期と前期)
SELECT report_date, tag, minutes, work_item_count
  FROM daily_report_tag_days WHERE report_date BETWEEN ? AND ?;
-- 3 最近の流れ・スパークライン: 直近12期間の日ごとの合計(タグ別にはせず、アプリ側でグループへ寄せる)
SELECT report_date, tag, minutes FROM daily_report_tag_days WHERE report_date BETWEEN ? AND ?;
-- 4 時間帯とそのタグ(今期だけ。週の帯・時刻別プロファイル)
SELECT b.report_date, b.position, b.start_minute, b.end_minute, b.activity, b.duration_minutes, b.is_gap,
       (SELECT group_concat(t.tag) FROM daily_report_item_tags t
         WHERE t.report_date=b.report_date AND t.source='time' AND t.position=b.position) AS tags
  FROM daily_report_time_blocks b WHERE b.report_date BETWEEN ? AND ? ORDER BY b.report_date, b.position;
-- 5 作業項目＋主タグ  6 アプリ  7 知見(今期、新しい順)
-- 8 前後の期間に日報があるか: SELECT MAX(report_date) ... < from / SELECT MIN(report_date) ... > to
```

- 2と3は範囲が重なるので、実装では3の範囲（直近12期間＝今期と前期を含む）を1本で読み、アプリ側で切り分ける。
- どの表も主キーの先頭が `report_date` なので範囲検索で読める。行数の目安: 週 約1,000行（12週分の `tag_days` 約500行を含む）、月 約3,500行（12か月分の `tag_days` 約2,200行を含む）、日 約300行（直近28日の `tag_days` を含む）。D1の読み取り上限（5M行/日）に対して十分小さいが、**ページのたびに全期間を読むクエリは置かない**（2026-09-21の事故の教訓）。月の流れが重くなったら、12か月分は `GROUP BY substr(report_date,1,7), tag` にしてSQL側で畳む（読み取り行数は同じだが、返す行が減る）。
- タグ→グループの対応はD1に持たず、`DAILY_REPORT_TAGS` から引く。

**日の詳細**: 1・4〜7を当日だけ＋`markdown`、`parse_warnings`。前後の日報の日付、その週の7日分の `daily_reports`・`tag_days`（上の7行の帯用）、直近28日の `tag_days`（目盛り用）も同じbatchで読む。

### 9.2 集計の純関数（`app/lib/daily-report-summary.ts`）

D1に触れない関数に分け、vitestの node project でテストする（`daily-report-tags.ts` と同じ方針）。

- `periodRange(range, date)` → `{ from, to, prevFrom, prevTo, days, elapsedDays }`（週は月曜始まり、月は暦月。タイムゾーンは扱わず `report_date` の文字列で計算）
- `summarize(reports, tagDays, period)` → 主数値（1日平均・合計・ログなし・日数）、グループ別・タグ別の1日平均と合計、前期の1日平均と日数（目盛りを点線にするかの判定に使う）
- `trend(tagDays, periods)` → 期間ごと・グループごとの1日平均（スパークライン・スモールマルチプル）
- `timelineSegments(blocks)` → 帯（タグの等分、欠落、`other`）。`tagDailyReport()` の等分・端数の寄せ方と同じ規則にする
- `hourProfile(blocks, reportDays)` → 1時間ごと・グループごとの平均分と、その時間に記録があった日数
- `axisRange(blocks)` → 横軸の時間範囲
- `groupWorkItems(items)` → 見出しごとの出現日と代表の箇条書き

テストのfixtureは取り込み側と同じく架空のデータにする。

## 11. 採らなかった案・未確定

- **円グラフ・ドーナツ・ツリーマップ・サンバースト**: §3.2。
- **レーダーチャート**: 軸の並び順に意味が無く、並べ替えると形が変わる。面積で印象が決まり、正確さも低い。
- **カレンダーのヒートマップ（月・年）**: 量を色の濃さで読ませるので精度が低い。日報のある日が飛び飛びで、1年の濃淡は「日報があったか」をほぼ表すだけになる。月は日ごとの縦棒（Q4）で足りる。
- **アプリ別の推移グラフ**: アプリ名の揺れが大きく（127種）、使用回数の精度も低い。
- **知見の全文検索画面**: 最初は期間表示の中で読む。件数が増えて探せなくなったら `daily_report_notes` に `LIKE` で作る。
- **見出しの名寄せ**: 規則が増えるわりに効果が読めない。グループ順に並べて近くに置く方式で様子を見る。
- 視聴（`media`）は割合が大きいので、「視聴を除いた配分」の切り替えが欲しくなるかもしれない。使ってみてから決める。
